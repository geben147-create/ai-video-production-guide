# 배분·프로젝트 프로필·이전

## 무엇을 70%로 세는가

기본은 편집 계획의 장면 수다. 생성 모델이 70개라는 뜻도, 전체 생성 요청을 70회로 제한한다는 뜻도 아니다. 사용자가 말한 '약 70개'는 연결된 100장면 계획의 맥락에서 해석했다.

| 지표 | 계산 | 주의 |
|---|---|---|
| 영상 장면 비율 | AI 영상 장면 수 / 전체 장면 수 | 약 0.70을 구체적 개수로 고정하는 필수 조건 |
| 영상 시간 비율 | AI 영상 장면 초수 합 / 전체 초수 | 장면 길이가 다르면 위와 다름 |
| 최소 생성 단위 | 장면별 필요한 소스 클립 수 합 | 순차 5초 두 개면 2단위 |
| 실제 제출 수 | 요청 로그의 고유 작업 수 | 재시도·실패·대안까지 별도 집계 |
| 채택 수 | 최종 편집에 실제 사용한 결과 수 | 계획·성공 상태와 구분 |

새 프로젝트에서는 먼저 대본으로 시간 순서를 만든다. 총길이의 마지막 1/3 부근에 image_eligible_from_seconds를 정하고 앞부분·핵심 하이라이트를 영상으로 보호한다. 보호 장면을 지정한 뒤 뒤쪽 설명·비교·자료·여운을 사진 모션으로 배분한다. 비율 때문에 대본을 늘리거나 줄이지 않는다. 서로 다른 길이의 장면은 시작 시각으로 배치하되 경계에 걸친 중요한 행동은 온전히 영상으로 둔다.

100장면을 임의로 78개나 100개의 영상으로 바꾸지 않는다. 사진 수를 채우기 위해 초반이나 하이라이트를 사진으로 바꾸는 것도 금지한다. 구체적인 배분 수와 사진 효과 대상 목록을 먼저 확정하고 함께 지킨다. 과거 기록은 현재 사용자의 변경 지시보다 우선하지 않는다. 짧은 예고편도 100장면으로 늘리지 않는다. 새 기획의 영상 수는 floor(전체 장면 수 × 0.70 + 0.5)를 사용하며, 이미 사용자가 확정한 다른 개수는 실제 지시 근거를 기록한다.

## 실행 전 배분·이미지 선택 계약

- policy.video_scene_count: 확정한 영상 장면 수. 새 100장면 계획은 70이다.
- policy.allocation_basis: 새 약 70:30 계획은 default_70_30. 사용자 확정 개수가 따로 있으면 user_confirmed와 실제 지시의 위치·내용을 allocation_instruction에 기록한다. 에이전트가 예외를 만들려고 user_confirmed를 자체 승인처럼 쓰지 않는다.
- policy.photo_motion_ids: 사진 효과를 적용할 장면 ID의 명시적 허용 목록. 실제 photo_motion 행과 완전히 일치해야 한다. 그 외 장면은 AI 영상이다.
- 사진 행에는 정확한 source_image, photo_motion_reason, requires_new_action=false, image_review를 기록한다. 이유는 이미지 안의 어떤 정보를 어떤 효과로 전달하는지를 설명해야 한다. '후반이라서', '30개를 채우려고'만으로는 부족하다.
- 실제 이미지에서 대본을 전달할 수 있는 설명·비교·증거·여운 장면만 고른다. 신규 행동이나 물리적 사건이 필요한 이미지, 초중반, 보호 하이라이트는 사진 효과 대상이 아니다.

새 세션과 작업 재개 시 이 계약을 읽고 검증한다. 계획 검사 후 영상/사진 총수, 사진 효과 ID·파일·선정 이유를 출력한다. 실행 전에는 --execution 검사도 통과시킨다. pending 후보나 파일 미지정 상태를 통과시켜 실제 효과 작업을 시작하지 않는다. 검사기는 필드의 일치만 검사하므로 이미지 내용과 사용자 지시의 진위는 에이전트가 원본을 직접 확인한다. 사용자 승인 질문을 반복하는 절차가 아니다.

## 범용 예시

assets/example-plan-100.json: 100장면 × 5초 = 500초. 001–067은 영상, 후반 070·084·098을 하이라이트 영상으로 지정한다. 합계 영상 70 / 사진 모션 30 / 최소 생성 단위 70이다. 나머지 30개의 ID가 사진 효과 목록에 들어 있다. 이는 배분 예시이며 실제 입력 파일은 없고 이미지 검수는 pending이다. 따라서 계획 검사는 통과하고 --execution 검사는 실패해야 정상이다. 실제 주제·이미지·선정 이유를 넣고 직접 검수한 뒤 사용한다.

## 기존 로테르담 예시를 보존하는 방법

사용자가 제공한 cinematic-rank1/plan.json을 2026-09-09 읽어 확인한 값이다. 이 프로필은 해당 작품을 다시 열 때만 선택한다. 범용 기본 조건으로 확산하지 않는다.

| 항목 | 기존 계획 |
|---|---|
| 장면 | 100 |
| 초중반 영상 | 001–066 |
| 후반 보호 영상 | 068·070·071·081·093·097 |
| 영상 / 사진 모션 | 72 / 28 |
| 길이 | 510초 |
| 장면 023 | 10초 영상, 순차 5초 단위 2개 |
| 장면 100 | 10초 사진 모션 |
| 총 최소 생성 단위 | 73 |
| 영상 / 사진 시간 | 365초 / 145초 |
| 영상 장면 / 시간 비율 | 72% / 약 71.57% |
| 첫 사진 시작 | 335초 |

첫 사진이 정확히 2/3인 340초보다 5초 앞선다. 기존 승인 계획의 장면 경계이므로 340초 고정 규칙으로 덮어쓰지 않는다. 기존 모델 배치, 무료 확인, 작업 ID, 재생성 금지, 순차 진행, 일시정지 상태는 해당 프로젝트의 원본 기록에서 다시 읽는다. 이 범용 스킬이나 위 표만으로 제작을 재개하지 않는다.

## 기존 JSON을 v2.1로 옮길 때

1. 원본은 보존하고 사본에 version 2.1, topic, policy의 총길이·프레임률·기본 생성 초수·사진 허용 시작·목표 장면 비율·보호 장면 ID를 넣는다. 총길이와 시작 시각은 원본을 이용한다. 위의 확정 영상 수·배분 근거·사진 ID 목록도 작성한다.
2. frame_id는 보존한다. 각 행에 purpose, highlight, start_seconds, duration_seconds, generation_units, source_image, status, transition을 매핑한다. 아직 없는 소스는 null 또는 빈 문자열로 기록하고 approved라고 표시하지 않는다.
3. 사진 행에 motion_recipe, source_ids와 위 이미지 선택 계약을 넣는다. 기존 작업·해시·검수 기록 등 추가 필드는 유지 가능하다. 기존 ID의 중복 제출은 별도 실행 로그와 대조한다. source_image가 바뀌면 이미지 검수를 다시 한다.
4. 생성 단위는 계획상 최소 소스 수다. 실제 모델에 추가 핸들이 필요하면 그 수를 올리고 사유를 기록한다. 사진 행은 항상 0이다.
5. python scripts/validate_plan.py path/to/plan.json을 실행한다. 실제 작업 전에는 같은 명령에 --execution을 추가해 이미지 지정과 검수 기록도 검사한다. 이 검사는 파일 경로의 존재·영상 내용·견적·권리·실제 연결을 검증하지 않는다. 해당 검수는 별도 진행한다.

타임라인은 최종 점유 시간 기준으로 빈틈·겹침 없이 기록한다. 디졸브에 쓸 소스 핸들은 따로 확보한다. 전환을 추가했다고 총길이·나레이션이 조용히 줄어들지 않도록 한다.
